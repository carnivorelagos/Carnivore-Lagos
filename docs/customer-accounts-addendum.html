Customer Accounts & Scale

A full walk-through of the account-based ordering flow before any of it gets built — where it starts, where the current backend already helps, where it stops short, and what heavy traffic would do to it. Same review process as the original architecture document: nothing here is implemented yet.

Adopted, from your last two notes

  • Email is collected and verified once, at signup — never re-requested at checkout.
  • Phone number + SMS one-time code is the only login mechanism after signup.
  • An account is mandatory to place an order — but browsing the menu stays open to everyone, no login wall on that.
  • A real order-confirmation receipt email sends automatically after a successful payment. This wasn't built before; it's in scope now.

01 First-time signup

Two verifications, not one: the phone number proves who can log in later; the email proves where a receipt can actually land. They happen back to back, but only the first one is required before the account is usable at all.

1
Enter phone number

POST /api/auth/otp/request — a 6-digit code is texted to the number. Rate-limited by phone and by IP, because unlike admin-login throttling, abuse here has a direct SMS cost.

2
Enter the code

POST /api/auth/otp/verify — phone confirmed, a Customer row is created, a session cookie is issued immediately.

Decision baked inThey can browse and build a cart right now, on this session — full account access doesn't wait on the email step below.
3
Name and email

Asked once, right after phone verification — not buried at checkout. Email format is validated, nothing more, at this point.

4
Verify the email

POST /api/auth/email/verify/request sends a code or link; POST /api/auth/email/verify/confirm marks Customer.emailVerifiedAt.

5
Gate is at the money step, not the door

If they close the tab here, they keep full access — logged in, cart intact. Only POST /api/payments/initialize checks emailVerifiedAt. A dropped-off signup never costs them their cart; it just asks them to finish verifying the moment they try to pay.

02 Returning customer

1
Same phone-entry screen

Same POST /api/auth/otp/request endpoint as signup — it looks up the phone number itself and decides new vs. returning. One screen for both cases; the customer never has to know which one they are.

2
Enter the code, session issued

If emailVerifiedAt is still null from an unfinished signup, they're dropped back into step 3 of signup at the payment step — not before.

03 Checkout, accounts-only

1
Quote stays public

POST /api/checkout/quote needs no login — anyone can see what their cart would cost before committing to an account. Creates nothing, so there's nothing to protect.

2
Placing the order requires a session

POST /api/orders gains a requireCustomer() check — the same pattern requireAdmin() already uses. customerId attaches automatically; name/phone/email pre-fill from the profile but stay editable per order, in case they're ordering for someone else.

3
Payment initialize gets simpler

Today's "no email on file" error becomes unreachable — a verified email is guaranteed before an account can check out at all.

4
Receipt fires once, on success

Added inside applyPaystackOutcome — the one function both the verify route and the webhook already share — so it inherits the same idempotency that prevents double-processing. One payment success, one email, regardless of which of the two paths detects it first.

04 Order history & profile

1
Profile and history

GET /api/me · GET /api/me/orders · GET /api/me/orders/{orderNumber} — all auth'd by the session cookie, no query-string tricks needed.

2
The old share-link stays, on the side

Today's GET /api/orders/{orderNumber}?ref= — order number plus payment reference as a stand-in for a login — was built for a guest-only world, but it's still genuinely useful as a shareable receipt link (forward it to whoever's picking up the order). Recommend keeping it alongside the new authenticated history, not replacing it.

05 The case this doesn't cover yet

If a staff member ever takes an order over the phone or at the counter and keys it in on your behalf — there's no path for that today, and account-only checkout doesn't add one either. Every order still has to come from a signed-in customer hitting POST /api/orders themselves. If walk-in or phone orders are part of how the restaurant actually runs, that's a genuinely separate admin-side feature — flagged below as an open decision, not assumed either way.

What heavy traffic does to this

Accounts add one genuinely new stress point — OTP volume. Everything else either already scales or is an infrastructure/plan question, not a code one.

OTP rate limiting

The rate limiter is Postgres-backed, not Redis — a deliberate earlier call to avoid extra infra. Fine at moderate volume, but OTP traffic is higher-volume than admin login ever was, and abuse costs real SMS money on top of the usual DoS risk. Worth watching; Redis (Upstash, serverless-friendly) is the first upgrade to reach for once real signup volume shows up — not something to pre-build now.

Database connections

Neon's pooled connection via the serverless driver adapter was already built to survive function scale-out. Holds up — just keep an eye on your Neon plan's compute/connection ceiling as an ops number, not a code fix.

SMS provider throttling

Providers cap sends per second on lower tiers. A signup burst (a promo, a press mention) can hit that ceiling. The request route needs a timeout and a clear "try again" response rather than letting the function hang on a slow provider call.

Order creation under load

The idempotency-key race handling and the order-number collision retry (31⁶ ≈ 887M combinations) were already built for concurrent bursts. Accounts don't touch this path's correctness at all.

Function concurrency

Netlify scales functions horizontally by default, bounded by your plan's concurrency ceiling — worth a quick check if a real spike (a launch, a promo) is expected, but it's a plan setting, not something this codebase controls.

Still need your call, before any of this gets built

Is a verified email required to browse and build a cart, or only to pay?

Recommend — gate it at payment only. Losing someone's cart because an email hasn't arrived yet is a worse outcome than letting them shop first.

One phone-entry screen for both signup and login, or two separate flows?

Recommend — one screen. Same security either way; fewer decisions for the customer to make correctly.

Do staff ever need to key in walk-in or phone orders without a customer account?

Needs your answer — this determines whether an admin-side order-creation path is in scope alongside everything above.

Which SMS provider — Termii, Africa's Talking, or another?

Needs your answer — either works technically; this needs an account and API key from you regardless of which.

Email provider for verification codes and receipts?

Proceeding with Resend, unless you'd rather use one you already have an account with (Postmark, SES).

Keep the old order-number + reference share-link alive?

Proceeding with yes — it's harmless and useful as a forwardable receipt link.
